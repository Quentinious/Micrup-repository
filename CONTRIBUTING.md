# Командная разработка Micrup

## Перед началом

Нужны Jira key, исполнитель, цель, acceptance criteria, зависимости и границы задачи. Для API сначала согласуйте контракт с Android/backend; для спорного бизнес-правила запишите решение в Jira. Соседняя бизнес-функция не добавляется в foundation-задачу.

## Ветки и коммиты

Все изменения — в отдельной ветке от актуального main:

```bash
git switch main
git pull --ff-only origin main
git switch -c feature/SCRUM-23-pr-workflow
```

Формат: `feature/<JIRA-KEY>-short-name`. Коммит: `[SCRUM-23] Document team workflow`. Один PR решает одну основную задачу; сопутствующие исправления явно перечисляются.

```bash
git add README.md CONTRIBUTING.md
git commit -m "[SCRUM-23] Document team workflow"
git push -u origin feature/SCRUM-23-pr-workflow
```

Добавляйте только проверенные файлы задачи. Не коммитьте секреты, local.properties, результаты сборки и реальные персональные данные.

## Pull Request и review

1. PR направляется в main, заголовок — `[SCRUM-23] Short description`; заполните template.
2. Укажите Jira, проблему/результат, изменения, проверки и границы задачи. Для UI — демонстрацию состояний, для API — примеры.
3. Незавершённая работа — Draft. До Ready for review выполните проверки затронутого модуля и проверьте CI.
4. Другой участник проверяет acceptance criteria, код, ошибки, контракт и миграции. До merge требуется минимум одно **APPROVED** независимого reviewer. Комментарий, реакция и автоматическая сводка не заменяют approval.
5. Ответьте на замечания. После изменения проверенного результата требуется повторная проверка reviewer.
6. Merge — после approval, успешных обязательных Checks и закрытия conversations. После merge feature-ветку можно удалить.

[Настройки GitHub](docs/github-workflow.md) обеспечивают процесс технически. Пока защита не включена, правила соблюдаются вручную; настройка остаётся открытой.

## Синхронизация и конфликты

```bash
git fetch origin
git switch feature/SCRUM-23-pr-workflow
git merge origin/main
```

После обновления повторите затронутые проверки. Спорный конфликт согласуйте с автором другой задачи. Не переписывайте историю общей ветки и не делайте force push в main.

## Контракт и миграции

OpenAPI и словарь данных определяют имена, типы, nullable, enum и ошибки. Изменение контракта согласуют Android и backend до реализации. Примеры — синтетические. Endpoint в OpenAPI ещё не является работающей функцией.

Уже merged/applied миграция Flyway не редактируется для добавления бизнес-модели: следующая миграция создаётся в задаче реализации.

## Jira и завершение

- «К выполнению»: не взята. «В работе»: есть исполнитель и работа. «В процессе проверки»: результат доступен для review/test.
- «Готово»: проверены acceptance criteria и согласования; для кода/документации PR merged, проверки успешны; для интервью/UX приложены результаты.
- В задаче нужны ссылка на результат и ограничения. Один merged PR не закрывает автоматически все связанные задачи.
- Блокер фиксируется с необходимым решением и зависимыми задачами.

Naming согласуется командой, защита проверяется в SCRUM-23. Публикация этого файла не является доказательством согласования.
